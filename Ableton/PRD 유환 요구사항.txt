좋아, 이번엔 **개발자 친구에게 바로 전달 가능한 PRD 형식**으로 정리해줄게.
네가 원하는 건 단순 “랜덤 MIDI 생성기”가 아니라,

**1) DB 기반으로 학습된 MIDI 생성 모델**이 있고
**2) 사용자가 원하는 코드 진행을 입력하면**
**3) 그 코드 진행에 맞게 실제 노트를 배치해서 MIDI를 생성**하고
**4) 그걸 가능하게 하기 위해 별도 화성엔진이 코드-노트 정합성을 관리하는 구조**

이거지.

아래 문서는 그 방향으로 썼어.
친구한테 보여줘도 되게 **제품 목적 / 시스템 구조 / 모델 역할 / 데이터 구조 / 학습 방식 / 추론 방식 / MVP 범위**까지 넣어둘게.

---

# PRD

## 프로젝트명

**조건부 MIDI 생성 시스템 (Harmony-Guided MIDI Generation System)**

---

# 1. 프로젝트 개요

## 1-1. 목적

사용자가 원하는 **코드 진행(Chord Progression)** 또는 **화성 흐름**을 입력하면,
시스템이 내부에 구축된 MIDI 데이터베이스(DB)를 바탕으로
그 코드 진행에 맞는 **실제 MIDI 노트 시퀀스**를 자동 생성하는 모델을 만든다.

이 시스템은 단순히 “분위기만 비슷한 MIDI”를 생성하는 것이 아니라,
다음 두 가지를 동시에 만족하는 것을 목표로 한다.

1. **음악적으로 자연스러운 패턴 생성**
2. **사용자가 지정한 화성(코드 진행)에 대한 높은 일치도**

즉,
이 프로젝트의 핵심은 **패턴 생성 모델 + 화성엔진**의 결합이다.

---

## 1-2. 핵심 아이디어

기존의 많은 생성 모델은 MIDI를 “통째로 생성”하는 데는 강하지만,
사용자가 원하는 정확한 코드 진행에 맞춰
**노트를 안정적으로 제어**하는 데 약하다.

그래서 본 프로젝트에서는 다음과 같이 역할을 분리한다.

* **MIDI 생성 모델**
  → 리듬, 패턴, 보이싱, 프레이징, 장식음, 움직임 생성 담당

* **화성엔진(Harmony Engine)**
  → 생성된 패턴을 사용자가 원하는 코드 진행에 맞게 해석/정렬/보정하는 담당

즉,
생성 모델이 “어떻게 움직일지”를 만들고,
화성엔진이 “어떤 화성 안에서 그 움직임이 성립해야 하는지”를 통제한다.

---

# 2. 제품 목표

## 2-1. 유저가 할 수 있어야 하는 것

사용자는 최종적으로 다음과 같은 작업이 가능해야 한다.

### 기능 A. 코드 진행 기반 MIDI 생성

예:

* `C - Am - F - G`
* `Dm7 - G7 - Cmaj7`
* `i - VI - III - VII`
* 특정 조성 기준 로마 숫자 진행

입력하면 해당 진행에 맞는 MIDI를 생성

### 기능 B. 패턴 재배치

기존 DB에 있는 MIDI 패턴 혹은 학습된 패턴 스타일을 가져와서
사용자가 원하는 코드 진행에 맞게 노트를 재배치

예:

* 기존 패턴은 Cmaj7 기준인데
* 유저가 `Ebmaj7 - Cm7 - Abmaj7 - Bb7` 진행을 넣으면
* 동일한 리듬감/움직임 구조를 유지하면서 노트를 새 화성에 맞게 재매핑

### 기능 C. 화성 중심 제어

유저는 단순 키워드가 아니라 음악적으로 제어하고 싶어함.

예:

* “이 진행에서 텐션 많이 쓰기”
* “너무 재즈스럽지 않게”
* “루트/3도/7도 위주”
* “아르페지오보단 패드형 보이싱”
* “베이스 무빙은 단순하게”
* “멜로디성 상성부를 유지하면서 코드톤 중심”

---

## 2-2. 제품 성공 기준

다음 조건을 만족하면 1차 성공으로 본다.

1. 사용자가 코드 진행을 입력하면 MIDI가 생성된다.
2. 생성 결과가 해당 코드 진행과 음악적으로 충돌하지 않는다.
3. 리듬/패턴은 기계적 복붙이 아니라 실제 연주처럼 자연스럽다.
4. 같은 코드 진행에도 여러 변형을 생성할 수 있다.
5. 향후 장르별 확장이 가능하다.

---

# 3. 문제 정의

## 3-1. 해결하려는 문제

기존 MIDI 생성 방식에는 아래 문제가 있다.

### 문제 1. 코드 제어가 약함

모델이 전체적인 분위기는 맞춰도
정확히 원하는 코드 진행에 맞는 노트를 내놓지 못할 수 있다.

### 문제 2. 패턴은 좋은데 화성이 틀어짐

좋은 리듬/패턴이 생성돼도
실제 코드톤 배치가 어긋나면 사용 가치가 크게 떨어진다.

### 문제 3. 사람 작곡 workflow와 다름

실제 작곡가는 보통:

* 코드 진행을 먼저 정하고
* 그 위에 패턴/보이싱/라인을 얹는다

그런데 많은 생성 모델은 이 구조를 그대로 반영하지 못한다.

---

## 3-2. 제품 철학

이 시스템은 “음악을 몽땅 확률로만 생성하는 모델”이 아니라,
**화성적으로 제어 가능한 생성기**를 목표로 한다.

즉,

* 생성은 유연하게
* 화성은 엄격하게
* 해석은 최소 환각으로
* 관측 MIDI는 최대한 보존

이 철학을 따른다.

---

# 4. 사용자 시나리오

## 4-1. 대표 사용자

* 작곡가
* 게임음악 제작자
* BGM 제작자
* MIDI 작편곡자
* 패턴 스케치가 필요한 프로듀서

---

## 4-2. 대표 사용 흐름

### 시나리오 1. 코드 진행만 넣고 생성

1. 사용자가 코드 진행 입력
2. 장르/스타일 선택
3. 길이 선택 (4마디 / 8마디 / 16마디)
4. 시스템이 MIDI 생성
5. 사용자 DAW에서 수정

### 시나리오 2. 기존 패턴을 새 코드에 맞게 변환

1. 사용자가 기존 MIDI 패턴 선택
2. 새 코드 진행 입력
3. 시스템이 패턴 구조는 유지하고 노트만 새 화성에 맞게 변환
4. MIDI export

### 시나리오 3. 특정 화성 성향으로 생성

1. 사용자 코드 진행 입력
2. “3도/7도 중심”, “텐션 적게”, “보수적 보이싱” 등 옵션 선택
3. 시스템이 그 조건을 반영해 생성

# 5. 시스템 구성

전체 구조는 아래처럼 본다.

## 5-1. 상위 아키텍처

### A. MIDI 데이터베이스 구축 모듈

* MIDI 수집
* 정리/정규화
* 트랙 분리
* 템포/박자/키/패턴 분석
* 화성 라벨링

### B. 화성 분석 엔진

* MIDI에서 구간별 화성 추정
* 루트 / 품질 / 텐션 / 베이스 판별
* 패턴이 어떤 화성 문법 안에 있었는지 기록

### C. 패턴 표현 추출기

* 각 MIDI를 “절대음”이 아니라 “화성 상대 표현”으로 변환
* 예: 코드 대비 scale degree, chord tone role, approach tone, passing tone 등

### D. MIDI 생성 모델

* DB에서 학습한 리듬/패턴/보이싱/움직임 학습
* 조건부 입력: 코드 진행, 장르, 길이, 밀도 등
* 상대적 패턴 생성

### E. 화성엔진(재배치 엔진)

* 생성된 상대 패턴을 입력 코드 진행에 맞게 실제 노트로 매핑
* 충돌 노트 보정
* chord tone / tension / non-chord tone 처리

### F. 후처리 엔진

* 음역 조정
* 중복 노트 정리
* 어색한 도약 수정
* 벨로시티/길이 보정
* MIDI export

# 6. 핵심 기능 명세

# 6-1. 화성엔진의 역할

이 프로젝트에서 화성엔진은 매우 중요하다.
이 엔진은 “코드를 분석하는 도구”이면서 동시에
“패턴을 새로운 코드 진행에 맞게 재배치하는 도구”여야 한다.

## 화성엔진이 해야 하는 일

1. MIDI 패턴이 어떤 화성 위에서 만들어진 것인지 분석
2. 각 노트가 화성 내에서 어떤 역할인지 판단
3. 새 코드 진행이 주어졌을 때 해당 역할을 유지하면서 노트를 재배치
4. 단순 이조가 아니라, 화성 문맥에 맞는 배치를 수행

---

## 6-2. 화성엔진의 내부 메커니즘

### 입력

* 원본 MIDI
* 박자/템포
* 마디 정보
* 필요시 유저 지정 코드 진행

### 출력

* 구간별 화성 라벨
* 각 노트의 역할 태그
* 화성 상대 표현
* 재배치 가능한 패턴 구조

---

## 6-3. 노트 역할 태깅

각 노트는 단순 pitch number가 아니라
화성 내 역할로도 표현되어야 한다.

예시 역할:

* Root
* 3rd
* 5th
* 7th
* Tension(9, 11, 13)
* Passing tone
* Neighbor tone
* Approach tone
* Pedal tone
* Bass anchor
* Structural tone
* Ornament tone

이렇게 해야 나중에 새 코드에 맞춰 바꿀 때
“이 노트는 그냥 C#이었음”이 아니라
“이건 당시 코드의 장3도 역할이었음”처럼 재사용 가능해진다.

---

## 6-4. 재배치 로직

예를 들어 DB에 있는 패턴이 아래 화성 위에서 생성되었다고 하자.

원본:

* Cmaj7 구간에서
* E G B D 같은 상행 패턴

이를 유저가 다음 코드에 적용하고 싶다:

* Abmaj7

그럼 단순 이조가 아니라
각 노트의 기능을 다음처럼 옮긴다.

* 3rd → C
* 5th → Eb
* 7th → G
* 9th → Bb

이런 식으로 “역할 유지 기반 매핑”을 수행한다.

---

# 7. 모델 설계 방향

## 7-1. 모델이 직접 해야 할 것

모델은 다음 요소를 학습해야 한다.

* 리듬 패턴
* 노트 밀도
* 상행/하행 흐름
* 반복과 변형
* 보이싱 형태
* 장식음 사용 방식
* 구간별 에너지 변화
* 프레이즈 구조

즉, 모델은 **음악적 움직임의 스타일**을 배운다.

---

## 7-2. 모델이 직접 하지 않아도 되는 것

다음은 모델이 전부 확률로 해결할 필요가 없다.

* 코드 정합성의 최종 판정
* 특정 코드에 대한 정확한 chord-tone 매핑
* 베이스 기준 재해석
* tension 허용 여부
* non-chord tone 정리

이건 화성엔진이 맡는 편이 훨씬 안정적이다.

---

## 7-3. 권장 표현 방식

생성 모델은 가능하면 **절대 pitch** 중심보다
**상대 표현** 중심으로 학습하는 것이 좋다.

예시:

* 절대음 C4, E4, G4
* 대신:

  * chord_degree = 1, 3, 5
  * octave_offset
  * rhythmic_position
  * duration
  * velocity
  * ornament_flag

이렇게 해야 같은 패턴을 다른 코드에도 쉽게 재사용 가능하다.

---

# 8. 데이터 설계

## 8-1. 필요한 DB 종류

### 1) 원본 MIDI DB

* 수집한 MIDI 원본 파일
* 장르/스타일/템포/박자 메타데이터 포함

### 2) 화성 분석 결과 DB

* 각 마디/구간별 코드 라벨
* 베이스 라벨
* 노트 역할 태그

### 3) 패턴 단위 DB

* 특정 마디 혹은 프레이즈의 패턴을 분리 저장
* 리듬 패턴
* 음형 구조
* 보이싱 구조
* 화성 상대 표현

### 4) 학습용 토큰/시퀀스 DB

* 모델 학습에 쓰는 전처리 결과물
* 상대 도수 기반 또는 이벤트 기반 시퀀스

---

## 8-2. MIDI 전처리에서 중요한 요소

다음 요소들은 반드시 저장/정규화 대상이어야 한다.

* pitch
* onset
* duration
* velocity
* bar/beat/subbeat 위치
* track/instrument role
* register(음역)
* chord segment id
* note function tag
* phrase boundary
* quantized position + original timing offset

---

## 8-3. 왜 timing offset도 필요한가

모든 걸 정박 퀀타이즈만 해버리면 인간적인 연주감이 사라질 수 있다.
그래서 아래 두 층을 같이 보관하는 게 좋다.

1. **구조용 정규화 데이터**
   → 모델 학습 안정용

2. **원본 미세 타이밍 정보**
   → 후처리에서 humanize 복원용

---

# 9. 화성 분석 엔진 요구사항

이 부분은 지금까지 너랑 계속 다듬어온 핵심이니까
개발자에게도 명확히 전달해야 해.

## 9-1. 분석 철학

화성 분석 엔진은
**겉보기에 그럴듯한 이름을 붙이는 엔진**이 아니라
**관측된 MIDI 노트를 최대한 정확하게 설명하는 엔진**이어야 한다.

---

## 9-2. 우선 원칙

1. 베이스를 절대 가볍게 무시하지 않는다.
2. 관측된 pitch set을 먼저 존중한다.
3. 상부 구조만 보고 루트를 멋대로 바꾸지 않는다.
4. 직접적인 same-root 해석이 가능하면 그걸 우선한다.
5. secondary dominant 같은 기능적 해석은 직접 해석보다 후순위다.
6. 멜로디적/아르페지오적 움직임을 너무 빨리 독립 화성으로 승격하지 않는다.
7. 사람이 실제로 연주한 MIDI라는 점을 고려해야 한다.

---

## 9-3. 분석 결과가 해야 하는 일

분석 결과는 단순 chord label 하나가 아니라
아래 정보가 있어야 좋다.

* root
* bass
* chord quality
* extension/tension
* omitted tones
* confidence
* observed notes
* structural notes vs ornamental notes
* candidate alternatives

이렇게 해야 나중에 패턴을 재배치할 때도 활용 가능하다.

---

# 10. 생성 파이프라인

## 10-1. 학습 전 단계

1. MIDI 수집
2. MIDI 정규화
3. 마디 분할 / 구간화
4. 화성 분석 엔진으로 코드 라벨링
5. 노트 역할 태깅
6. 상대 패턴 표현 생성
7. 학습 데이터셋 구축

---

## 10-2. 추론 단계

사용자가 코드 진행을 입력하면:

1. 코드 진행 파싱
2. 각 구간의 화성 표현 생성
3. 생성 모델이 상대 패턴 생성
4. 화성엔진이 각 노트를 실제 pitch로 매핑
5. 후처리 엔진이 음역/중복/도약/벨로시티 보정
6. MIDI export

---

# 11. 입력/출력 스펙

## 11-1. 입력

필수 입력:

* 코드 진행
* 길이(마디 수)

선택 입력:

* 장르
* 템포
* 박자
* 밀도
* 보이싱 성향
* 텐션 허용도
* 리듬 복잡도
* 악기 역할(피아노, 스트링, 베이스 등)

---

## 11-2. 출력

* MIDI 파일
* 구간별 코드 매핑 정보
* 생성에 사용된 패턴 메타정보
* 선택적으로:

  * chord-tone / non-chord-tone 표시
  * confidence score
  * variation seed

# 12. MVP 범위

처음부터 너무 크게 가지 말고
MVP는 아래 정도가 현실적이다.

## 12-1. 1차 MVP 목표

* 단일 악기 기준 생성
* 4마디~8마디
* 피아노 또는 키보드 계열
* 4/4 박자 우선
* 기본 장르 1개부터 시작
* 코드 진행 입력 기반 생성
* 화성 상대 패턴 재배치 가능

---

## 12-2. MVP에서 제외 가능

* 멀티트랙 전체 자동 생성
* 드럼/베이스/스트링 동시 생성
* 복잡한 폴리리듬
* 자유로운 템포 변화
* 아주 긴 곡 구조 생성
* 오디오 렌더링

---

# 13. 기술 방향 제안

## 13-1. 구현 방식 후보

### 방향 A. 규칙 기반 화성엔진 + 시퀀스 생성 모델

가장 현실적이고 안정적

* 화성엔진: 규칙 기반
* 생성 모델: Transformer / sequence model
* 장점: 제어력 높음
* 장점: 디버깅 쉬움
* 장점: 사용자가 원하는 코드 진행 반영 쉬움

### 방향 B. Retrieval + Rearrangement

DB에서 유사 패턴을 찾고 그걸 재배치

* 장점: 데이터가 적어도 시작 가능
* 장점: 결과가 비교적 자연스러움
* 장점: MVP 빠름
* 단점: 완전 생성 자유도는 낮음

### 방향 C. Hybrid

* 먼저 retrieval로 패턴 후보 가져오고
* 그 위에 생성 모델이 variation 생성
* 마지막에 화성엔진이 보정

이게 장기적으로 제일 좋다.

# 14. 권장 개발 순서

## Phase 1. 화성엔진 완성

가장 먼저 해야 할 것:

* MIDI 분석
* 코드 라벨링
* 노트 역할 태깅
* 상대 패턴 표현 추출

이게 안 되면 나중에 생성 모델이 있어도 제어가 안 된다.

---

## Phase 2. 패턴 DB 구축

* 화성별 패턴 정리
* 리듬 패턴 추출
* 보이싱 패턴 추출
* phrase 단위 저장

---

## Phase 3. Retrieval 기반 MVP

* 유저 코드 진행 입력
* DB에서 유사 패턴 검색
* 화성엔진으로 재배치
* MIDI 출력

이 단계만 돼도 이미 꽤 유용할 수 있다.

---

## Phase 4. 생성 모델 추가

* retrieval 결과를 바탕으로 variation 생성
* 또는 처음부터 상대 패턴 시퀀스 생성

---

## Phase 5. 고도화

* 멀티트랙
* 장르 확장
* 구조 생성
* 인간적인 연주 표현 고도화

# 15. 비기능 요구사항

## 15-1. 제어 가능성

개발 목표는 “좋은 결과 1개”보다
“유저가 원하는 방향으로 조정 가능한 시스템”이다.

## 15-2. 해석 가능성

결과가 왜 그렇게 나왔는지
개발자가 디버깅할 수 있어야 한다.

## 15-3. 확장성

장르별 DB 추가, 악기 추가, 패턴 타입 추가가 가능해야 한다.

## 15-4. 재현성

같은 seed / 같은 입력이면 동일 결과 재현 가능해야 한다.

---

# 16. 리스크

## 리스크 1. 데이터 라벨링 비용

좋은 화성 분석/역할 태깅이 매우 중요하므로
전처리 품질이 전체 성능을 좌우한다.

## 리스크 2. 생성 모델 단독 접근의 한계

모델만으로 모든 화성 제어를 해결하려고 하면
결과가 불안정해질 수 있다.

## 리스크 3. 절대 pitch 중심 학습의 한계

전조/코드 변경 대응력이 떨어질 수 있다.

## 리스크 4. 과도한 기능 해석

화성 분석 엔진이 너무 예쁘게 해석하려 하면
실제 관측 MIDI와 멀어질 수 있다.

---

# 17. 최종 제품 비전

이 시스템의 최종 목표는
“DB에 있는 MIDI들을 학습하고,
사용자가 원하는 코드 진행이나 화성 흐름에 맞춰
실제로 쓸 수 있는 MIDI 노트를 생성해주는
화성 제어형 MIDI 생성 엔진”이다.

핵심은 다음 한 문장으로 정리된다.

> **패턴은 생성 모델이 만들고, 화성 정합성은 화성엔진이 책임진다.**

즉,

* 생성의 자유도
* 화성의 정확성
* 작곡가가 원하는 제어력

이 세 가지를 동시에 잡는 구조다.
